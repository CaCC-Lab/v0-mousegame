## 実装中に分かったこと

1つ目は計画外の不具合で、**直していない**。2つ目と3つ目は実装中に踏んで直したもので、次に同じ型を踏まないための記録。

- **キーボードでスイカを取れない**: Enter で選んだ果物を取るとき、スイカの操作を `click` として渡している（`components/FruitHarvestGame.tsx` の `getInteractionTypeForFruit`）。スイカの正解は `drop` なので、キーボードでは必ずミスになる。アクセシビリティ（キーボード操作）の約束と食い違う。v1.1 の G には入っていないので、判断して別タスクにする
  - **2026-09-24 直した**: 独自の対応表を消し、得点計算と同じ `getRequiredInteraction` から引く。unit `KeyboardHarvest`（4種類すべてキーボードで得点が入る）
- **jsdom では通るが実ブラウザで動かない**型の不具合が1件出た（`?test=1` の自動開始）。実ブラウザは毎フレーム再描画するため、描画ごとに作り直される関数を effect の依存に入れると、待ち時間つきの処理が張り直され続けて発火しない。e2e で見つけ、ref から呼ぶ形に直した
- `next build` の型検査でしか出ない不具合が1件出た（配置の `as const` による型の狭まり）。jest は型を見ないので、**コミット前に `npx tsc --noEmit` か `next build` を通す**
- **ヘッドレス WebKit で、収穫が続くと処理が追いつかない**（2026-09-24、**直していない・実機未確認**）: `?test=1` の自動プレイ（0.4 秒ごとに収穫）で、約 80 秒でゲーム時間が約 30 秒しか進まず、収穫も約 32 回（本来は約 200 回）。1並列でも同じ。タイマーの張り直しは無い（`finishGame` の依存は安定）ので、ページ全体の処理の遅れ。Linux のソフトウェア描画に特有か、実機の Safari でも起きるかは分からない。**実機の Mac／iPad の Safari で、速く取り続けたときに残り時間の進みが遅くならないかを確かめる**。e2e の G12 は WebKit だけ `fixme` にして理由を書いた
- **Playwright の `locator.click()` で「はじめる」を押すと、Firefox でページが最下部までスクロールすることがある**（45回中11回）。座標で直接押すと105回で0回。人の操作では起きないと判断し、コードは直さず、e2e の開始を座標クリックにした（`e2e/v1.1-play-fixes.spec.ts` の `startArcadeByMouse`）

- **e2e のフレーク（再試行で通過）**: Firefox の `fever-and-legend` 「はじめて発動したときに…」（2026-09-24 の全体実行で1回）、Firefox の `itch-release-verification` (7) ブルーベリーのダブルクリック（2026-09-24 の1回前の全体実行で1回）。どちらも再試行で通った。繰り返し落ちるようなら実際の不具合として調べる
- **1280×800 より小さい画面での果物の重なり**（2026-09-24 測って直した）: 1024×768・1280×720・1366×768・1920×1080 は 0 だった。800×600 だけ、15回開始×12個で重なり 29 組・覆われ 4・凡例と重なり 18 だった。原因は2つ。(1) 配置が 1280×800 基準の大きさで見積もっていた (2) **800 幅では遊び始めるとヘッダが3段に折り返して 44→160px になり、プレイエリアが 476→308px に縮む**ので、開始時点の大きさで置いた果物が縮んだ後に重なる。実際の大きさを測って配置に渡し、大きさが変わったら重なった果物だけ置き直し、帯とすき間に px の最低限を設けた。3ブラウザとも 0。unit `fruitPlacement`（小さいプレイエリア・`relayoutFruits`）、e2e「小さい画面でも果物が重ならない」
- **800 幅でヘッダが3段に折り返し、プレイエリアの半分近くを取る**（2026-09-24 発見、**直していない**）: 上記の測定中に分かった。プレイエリアは 600px の画面で 308px。ヘッダの並べ方（フィーバーゲージ・得点・時間・ベスト）を狭い幅向けに詰めるかは画面構成の判断なので、v1.2 の候補に回す
